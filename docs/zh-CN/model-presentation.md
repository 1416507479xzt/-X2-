# 模型统一决策与真机表现接入

## Windows 仿真启动

在 `example/x2_agent` 目录运行：

```powershell
python agent.py --competition-mode --health-semantic model --presentation-backend unity
```

保持模拟器运行。连接后不打招呼，先说“灵犀灵犀”（兼容“林夕林夕”）。
开场使用独立模型任务，只返回`reply/emotion/gesture`，程序根据已确认的唤醒事件附加
`intent=greeting/action=continue`，不再让模型重复分类开场；不接受缺字段或多个问句。
健康回答、回顾原话、明确动作请求都经过模型。普通对话模型每次返回
`intent/action/reply/emotion/gesture`；`action`是问询流程决策，不是硬件动作编号。
程序验证JSON、问询轮数和能力白名单；TTS只接收reply，表情动作在首个音频包前下发。
这仅是同步发起，不保证真机扬声器与屏幕、机械臂达到毫秒级同步。

正常回答不调用关键词健康分类器。唤醒仍采用本地拼音匹配。
旧的`auto/rules`分支保留，但不是默认竞赛模式。未加`--competition-mode`仍是原普通示例，
不应把普通模式或旧模式的表现当作新模式验收。

## 模型可以选择的表现

| 模型选择 | Unity映射 | AimDK 1.1映射 |
|---|---|---|
| emotion=null | 不发新表情 | 不发新表情 |
| neutral | emotion/neutral | PlayEmoji emotion_id=10 |
| happy | emotion/happy | PlayEmoji emotion_id=90 |
| sad / surprised / angry | 同名技能 | emotion_id=110 / 140 / 180 |
| sympathy | emotion/love | PlayEmoji emotion_id=120 |
| admiration | emotion/love | PlayEmoji emotion_id=200 |
| gesture=null | 不发动作 | 不发动作 |
| wave_hands | gesture/wave_hands | SetMcPresetMotion motion=1002 area=2 |
| open_arms | gesture/open_arms（近似张开双臂） | motion=3008 area=11（拥抱姿态） |

Unity目前只有六种视觉表情、两种动作；sympathy与admiration都近似显示爱心，
不是不同的动画。不能把SDK的200“崇拜”误作同情。
AimDK目录扩展为20种表情和20种预设动作，包括思考、严肃、鼓掌、比心、
加油、鞠躬等；完整编号与语义在`x2_agent/presentation.py`。
没有开放伪造故障/充电状态、握手等接触动作或行走控制。
目录按后端传给模型，并包含语义说明；不向Unity宣称它具有全部真机动画。
本次Python修改不会为便携版模拟器增加动画，需要新增动画时必须修改Unity工程并重新构建。
模型可以自主选择配合语言的表现，也可以不做动作；否定和拒绝应由模型理解。
不是按关键词映射，不强制轮换表情；自然倾听可选择neutral，不应每轮重复sympathy。
日志记录模型选择与下发结果，最近网关回执也传入模型，但回执未可靠关联轮次，
不能把它当成当前动作的完成证明，也不自动重试失败动作。
安全层检查控制权、参数和频率，但不宣称能确定性验证模型是否理解了所有否定句。

## AimDK表现后端

代码提供可选 `--presentation-backend aimdk`，仅处理表情与预设动作。它依赖PC2上的
ROS2/rclpy和匹配固件的aimdk_msgs，Windows仿真不导入这些依赖。
启用还需要显式传入`--enable-robot-presentation`，并使用竞赛model模式。
**这不是完整真机启动指南：ASR输入和TTS输出仍走现有WebSocket网关，独立ROS音频桥尚未实现。**
没有经过验证的音频网关/桥接时，不能仅切换这个参数就宣称可以独立上真机。

接口：
- `/aimdk_5Fmsgs/srv/PlayEmoji`：mode=1单次，priority=1，不覆盖系统故障高优先级提示；
  依据外层success判断受理，不依据未启用的header。
- `/aimdk_5Fmsgs/srv/GetMcAction`：动作前要求action_desc为STAND_DEFAULT且status.value为100，
  响应成功；不依赖v0.8.2起弃用的current_action数值。
- `/aimdk_5Fmsgs/srv/SetMcPresetMotion`：interrupt=false；不自动切换运动模式。

ROS节点在生命周期内复用，不为每次动作新建进程或节点。动作最小间隔8秒；
查询超时、状态未知或切换中一律阻止动作。写入超时标记unknown，不盲目重试，
因为超时不代表设备没有执行。当前只记录sent/accepted/rejected/blocked/unknown，
不将受理等同于完成，也尚未实现真实动作结束与表情完成反馈闭环。

## 验收与限制

1. 无唤醒不说话；唤醒后由模型问候，不使用固定人名。
2. 说“今天有点累”，检查日志route=health_model，而不是health_rules。
3. 先说脖子不适再说腰酸，再询问之前提到的问题；核查两条原话都在模型上下文中。
4. 说“请挥挥手”和“不要挥手，只聊一会儿”；检查实际技能下发与用户意图一致。
5. 控制台接管后不得继续下发动作；不支持的动作应解释限制。
6. 故障或非法模型输出不得下发动作，不播JSON；首包音频前失败不得提前动作。

离线单元测试覆盖结构校验、路由、记忆、控制权变化、TTS失败和SDK参数映射；
不等同于在线模型准确率、Unity视听效果、低于2秒延迟或真机验收。
8秒模型超时是故障上限，不是正常响应延迟保证。当前等待完整JSON校验后才启动TTS，
真实延迟需测量后继续优化。

## 回顾与纠正回归检查（2026-10-20）

模型新增`correction`意图，必须配合`action=continue`，不消耗健康问询轮数。
历史原话保留，模型应根据后来的明确纠正理解现状；并未建立持久化健康档案。
回顾/纠正的语义仍由模型判断，不通过关键词强制路由。

重新启动后依次演示：

1. 唤醒，说明腰酸，再说明脖子疼。
2. 插入“向我挥挥手”，然后问“我今天哪里不舒服？”。
   应回顾腰酸和脖子疼，而不是要求重新描述。
3. 问“我刚才说了哪几个部位不舒服。”（即使识别成句号也应理解）。
4. 说“脖子已经不疼了，但腰还是酸”，再问“现在还有哪里不舒服？”。
   应区分旧症状与最新纠正，不能遗漏腰酸。
5. 针对先前不妥回答提出质疑，检查是否承认并明确更正，而不是继续维护原建议。

出现兜底时查找`模型输出失败 reason=`：可区分非法JSON/重复键、字段错误、
意图与流程冲突、能力不可用、追问限制、输出过长、超时或服务/流异常。
日志同时记录输出字符数、耗时及历史条数，不记录模型原文或异常消息。
`provider_or_stream_error`仍是错误类别，不是具体服务原因。
新增离线测试验证上下文传递、纠正留存、协议与诊断脱敏，不证明真实模型语义正确率。

### 失败恢复

不可用、冷却中或非法的表情/动作字段仅置空，不替换成其他动作；
语言和流程仍须通过校验，日志显示`模型表现降级 dropped=...`。
这不是对语言语义的确定性安全审查；提示明确禁止承诺动作必然执行，
仍需在线验收是否出现说了要做但实际取消的情况。

格式或流程错误最多请求模型重新生成一次，不直接强改意图或删除问句。
首次生成与修正共用8秒时限（流关闭清理可额外占用少量时间）；
超时、服务异常、工具调用及超长输出不继续重试。修正未通过才进入兜底。
动作执行不重试，控制权/冷却/站立状态校验仍保留。
日志区分`too_many_questions`与`close_contains_question`，修正成功有明确记录。

正常对话的生成失败、TTS失败或取消后保留用户原话，标记`response_status=unanswered`，
不增加健康问询轮数，不记录未成功播报的回答，也不把原话自动认定为当前健康事实。
这些记录与其他对话一样最多保留64轮，仅存在当前进程。

## 开场与后续服务更新（2026-10-21）

开场两轮限制只约束主动健康问询。用户后续新增不适、求助或回答求助澄清时，
模型使用`other/continue`，可提出一个必要问题，不重新开始迎宾，不凭症状关键词路由。
模型仍负责回答、语义和表现选择；安全层不执行超范围动作。

`x2_agent/care_reference.py`包含核对过的NHS公开健康教育摘要（颈部、睡眠、腹部不适）。
整份小资料集传给模型，由模型结合上下文判断适用性，并非固定台词库或完整医疗分诊系统。
不包含药物剂量或治疗动作，不能替代个人医嘱。来源页面及核对日期保留在代码中。
NHS页面的英国急救号码未复制到中国部署。临床适用性和最终现场演示仍需审核。

可选真实模型文本测试（消耗API用量、不连接机器人）：

```powershell
python scripts/check_care_dialogue_live.py --live
```

每次3次开场+6轮合成对话，每次生成最多修正一次；只使用合成案例，不发送真实健康档案。
2026-10-21测试了两组，第二组3次开场均成功，6轮对话均有有效结果，没有触发兜底。
颈部求助不再一概拒绝，能使用资料提示。仍观察到休息建议和腹部风险提示重复，
第一轮有时仅追问、针对性安抚不足；真实模型仍可能遗漏/改变资料中的条件。
这是小样本人工观察，不代表临床安全保证、零失败率、语音时延或完整比赛验收。

### 简短确认与再次交流（2026-10-21）

模型新增`acknowledge`（仅确认/致谢）和`reengage`（再次招呼）意图，都使用continue，
不推进健康问询。是否属于这两类由模型判断，不按“好的”等词强制路由。
acknowledge最多15字、不含问句，超出时请求一次受限修正，不截断句子或替换固定台词。
开场health/followup要求先有一个陈述句再问问题，纯提问会请求修正；该结构检查
不能证明陈述内容有共情或针对性，仍需人工检查，且修正增加生成时间。

conversation_state记录上次是否明确结束交流。decline标记ended；仅确认保持原状态；
重新接话/新请求等恢复engaged。它独立于interview_active，不清除旧记忆或重开问询。

文本复测：`python scripts/check_care_dialogue_live.py --live --scenario conversation`。
每组1次开场+10轮对话，最多22次模型调用，消耗API用量、不连接机器人。
最近一组连续“好的”均简短确认，结束后的问候能重新接话，带新增疼痛的确认未被当作纯确认。
仍有机械共情和重复休息建议，回顾也可能遗漏最新程度变化，不能作为最终语义验收通过。
两轮发生受限修正；实际语音延迟尚未测量。未改动ASR识别或机器人安全限制。

### 登记式开头清理

普通对话和开场输出在播报前清理完整的登记式引导分句，如“我记下您……啦”、
“您……我记下了”“我知道/了解您……”。只处理开头的有限模式，不匹配用户输入，
不生成健康建议；引用、回忆用语“我记得”和问句不删除。有效后文保留，通常不增加模型调用。
如果清理后为空，进入一次受限修正；若开场追问因此只剩提问，也仍需通过原有校验。
这不是所有生硬表达的语义检测，不保证拦截所有同义变体；不会清除用户原话或记忆。
腹部问询中重复已回答的问题与建议泛泛仍是独立的待改进项，不因清理开头而自动解决。

### 讲解时的手势选择

capabilities增加`explanation_gestures`与`explanation_note`，由模型根据建议/讲解语义
自主选用，不由程序按症状或“建议”关键词强制插入动作。Unity候选只有open_arms，
它仍是已有的双臂展开近似展示，不是新增的摊掌/指点动画。AimDK候选为左右举手，
没有把预设动作改成小幅度动作，不保证真机与仿真视觉一致。
控制权失效、8秒冷却时清空候选，执行前仍再次校验。简单确认、拒绝动作或急迫求助
不应例行做讲解动作；未实现语义层确定性安全审查，仍需现场监护与验收。

文本检查命令：`python scripts/check_care_dialogue_live.py --live --scenario presentation`。
本次一组5次生成中，讲解睡眠建议选择open_arms，确认与明确拒绝动作时均选择null；
最后一轮达到8秒超时。此脚本不发送技能，不证明模拟器已播放或真机已执行。
同时发现语言仍可能补充资料未收录的细节，不应将本次动作选择检查当作健康内容验收通过。

## 新增不适时主动给生活提示

用户报告不适时，大模型应主动选择资料中适用的一项具体照护提示，不再等“怎么缓解”的追问。
资料新增腰背不适的一般健康教育；所有资料一起交给模型，不按症状关键词拼接回复。
缺关键安全信息时先澄清，突发严重不适优先求助，不提供无依据的按摩、拉伸或用药。
否认部分症状不代表已排除全部危险，也不保证生活提示有效。

可运行 `python scripts/check_care_dialogue_live.py --live --scenario proactive` 做付费纯文本测试。
测试不连接机器人；模型可能仍漏给提示或输出校验失败，需人工审阅，不能视为医疗安全认证。
